The build check: why a task's app build kept failing, and what makes a task prove it builds
==========================================================================================

Report: "flutter builds fail, and this isn't the first time a task being turned
in has resulted in a broken app build, figure out what can be done to make sure
tasks which work on the app dont submit a broken build".  The build that failed
was tool/qr_install.sh's `flutter build apk --release`, in the main checkout:

  GeneratedPluginRegistrant.java:34: error: cannot find symbol
        flutterEngine.getPlugins().add(new io.flutter.plugins.sharedpreferences.SharedPreferencesPlugin());
    symbol:   class SharedPreferencesPlugin
    location: package io.flutter.plugins.sharedpreferences
  > Task :app:compileReleaseJavaWithJavac FAILED

1. The cause of that failure
----------------------------

Not a defect of the tree: a build of HEAD from an empty build/ passes.  It is
what happens when shared_preferences_android is raised from 2.5.0 to 2.5.2
(d0c681d, the R8 keep rules) over the build/ a person already has from 2.5.0.

Toolchain, all under scripts/.dev, none of it the machine's: Flutter 3.47.7
(tool/install_flutter.sh's archive, checksum verified), JDK 21.0.13, Android SDK
36 with build-tools 36.1.0, NDK 30.0.14904198 and CMake 4.1.2 (the pins of
android/gradle.properties), Gradle 9.3.1 from the wrapper.

  a. HEAD (fb6fd80), `flutter build apk --release` in an empty directory:
     built, 59.2 MB.  (pub get printed the same package list as the report:
     "shared_preferences_android 2.5.2 (2.5.3 available)", "1 package is
     discontinued", "14 packages have newer versions incompatible".)
  b. d0c681d^ (2.5.0) built (59.3 MB); then its pubspec.yaml and pubspec.lock
     replaced by HEAD's (2.5.2); `flutter build apk --release` again in the
     same directory:

       GeneratedPluginRegistrant.java:34: error: cannot find symbol
         symbol:   class SharedPreferencesPlugin
         location: package io.flutter.plugins.sharedpreferences
       Execution failed for task ':app:compileReleaseJavaWithJavac'.
       BUILD FAILED in 1m 9s

     The same message, the same line, and "location: package" means the package
     is on the classpath (the plugin's R class is in it) with the class missing.
  c. The plugin's Kotlin output after (b), build/shared_preferences_android/
     tmp/kotlin-classes/release/io/flutter/plugins/sharedpreferences/:

       broken (2.5.0 -> 2.5.2 over the old build/):
         FlutterError, MessagesAsync_gKt, MessagesAsyncPigeonUtils, Messages_gKt,
         MessagesPigeonUtils, SharedPreferencesApi*, SharedPreferencesAsyncApi*, ...
         -- no SharedPreferencesPlugin, LegacySharedPreferencesPlugin,
            SharedPreferencesBackend, ListEncoder
       good (a build of 2.5.2 from an empty build/):
         the same, and LegacySharedPreferencesPlugin, ListEncoder,
         SharedPreferencesBackend, SharedPreferencesPlugin, SharedPreferencesPluginKt

     Kotlin's incremental compiler keeps its state in build/, keyed by the
     paths of the sources, and a plugin's sources are in the pub cache under a
     directory named after its version (shared_preferences_android-2.5.0/ ->
     -2.5.2/).  Moved sources leave it with half the classes.
  d. Not it (tried): a plugin file lost from the pub cache.  With
     SharedPreferencesPlugin.kt removed, Flutter stops before Gradle with "The
     plugin `shared_preferences_android` doesn't have a main class defined".
     A stale GeneratedPluginRegistrant.java does not fit either: line 34 is
     SharedPreferencesPlugin in HEAD's registrant too (five plugins, same order).

The fix: android/gradle.properties says `kotlin.incremental=false`.
  e. The directory of (b), already broken, with the line added:
     `flutter build apk --release` built, 59.3 MB.  (It heals a build/ that is
     already like that.)
  f. A fresh run of (b) (2.5.0 built without the line; then 2.5.2 and the line
     together): built in 47 s, all plugin classes present, including
     SharedPreferencesPlugin.class.
  test/build_config_test.dart fails when the line is not there (checked by
  commenting it out).  tool/qr_install.sh's failure message now names "cannot
  find symbol" in GeneratedPluginRegistrant.java and `flutter clean`.

2. Why tasks keep handing in apps that do not build
---------------------------------------------------

  * A task's sandbox has no Flutter SDK, no JDK 17-21 and no Android SDK
    ($HOME is an empty tmpfs; /opt/android-sdk is not mounted), and nothing in
    scripts/test.sh, scripts/lint.sh, CLAUDE.md or hand_in ever asked for a
    build of harness_client/.  An earlier task that did build the app made a
    toolchain by hand under scripts/.dev and left no script behind.
  * Even a task that builds the app builds it from an empty build/ and so
    cannot see the failure above.
  * The app's own tests have been red for seven commits, unseen.  Bisect, each
    commit exported with git archive and run with `flutter analyze` and
    `flutter test` (pub get first):

3. What now stops it
--------------------

tool/check_build.sh (docs/dev-loop.md, "The Flutter app's build check"):
pub get --enforce-lockfile, analyze, test, `build apk --release` from an empty
build/, the build over the base's build when dependencies or android/ changed,
the tools' own tests when tool/ changed; a stamp for the commit on success.
.harness/plugins/dev/harness-client-check.el, this repository's plugin: hand_in
refuses a task of this repository that changed the app unless the stamp covers the
app as committed (test/harness-client-check-test.el).  The harness itself knows no
app: lisp/modules/harness-tools-handin.el only runs the async filter
task/before-hand-in, which any project's plugin may add a function to
(test/harness-tools-handin-test.el, which also checks that the tool names no
Flutter, Android, licence or harness_client).
tool/client_toolchain.sh installs what the sandbox lacks, pinned and checksummed.

Run on the change that broke the build, in a throwaway repository (base: d0c681d^
with 2.5.0; head: d0c681d, 2.5.2, Kotlin still incremental), with the toolchain
above, tool scripts added to both commits:

4. The toolchain, from an empty sandbox
---------------------------------------

`HARNESS_CLIENT_TOOLCHAIN=<empty dir> tool/client_toolchain.sh --accept-android-licenses`
on a machine with no Flutter, a JDK 27 and no Android SDK: 1m26s, and
Flutter 3.47.7 (2.5 GB), Temurin 21.0.13+9 (346 MB) and an Android SDK with
platform 36, build-tools 36.1.0, NDK 30.0.14904198, CMake 4.1.2 and
platform-tools (2.7 GB) were in it; the second run found them all and
downloaded nothing.  The downloads are pinned to a release and checked against
the publisher's checksum (Flutter's from tool/install_flutter.sh, Temurin's from
api.adoptium.net, the command-line tools' SHA-1 from Google's repository2-3.xml).

5. The check's own tests
------------------------

  python3 tool/test_check_build.py   (a fake flutter in a throwaway git repository)
  scripts/test.sh test/harness-tools-handin-test.el test/harness-client-check-test.el
  flutter test test/build_config_test.dart

Each was run with the behaviour it guards broken, and failed:
  check_build.sh: a ratchet that lets every test through; no second build in the
  upgrade step; --status that ignores app changes; a failing step that does not
  stop the check.
  harness-client-check.el: a gate that never refuses; a stamp that is never read;
  uncommitted changes ignored.

6. The check on this change itself
----------------------------------

A task's own flow, from nothing: no toolchain anywhere, no environment variable,
`harness_client/tool/check_build.sh --accept-android-licenses` in the task's
worktree (a sandbox whose $HOME is an empty tmpfs).  It installed Flutter, the JDK
and the Android SDK into .git/harness-client-toolchain (8.8 GB with the pub and
Gradle caches it filled), then:

  ok   pub-get            13s
  ok   analyze            14s
  ok   test               75s   383 tests: 352 passed, 31 failed, 0 skipped
       NOTE: all 31 failing tests already fail at fb6fd8002c40; this branch adds none.
  ok   build              217s
  ok   upgrade-from       158s    (android/gradle.properties differs from main's)
  ok   upgrade            28s
  ok   tool-test_qr_tools 95s
  ok   tool-test_check_build 7s
  check_build: PASSED in 607s for commit a69a79d3dd72
  check_build: release APK 59238635 bytes, sha256 237112134b3ea53722e3150fcbec5cfcffd31c1bae1044f069e2fe66a96fc902

(11 min 37 s with the toolchain installed; the next run finds it.)  `check_build.sh
--status` then says "the build check passed for a69a79d3dd72, and the app is
unchanged since", and the plugin's gate, asked about that worktree, refuses nothing:
harness-client-check--refusal => nil.  Committing an app change after the
check makes it answer "the app changed after the check passed for a69a79d3dd72:
harness_client/lib/extra.dart" with the command to run.

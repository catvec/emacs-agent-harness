# Phone installer verification

Run on 2026-10-19 from `harness_client` in the task worktree.  No phone or
Android SDK is visible to this sandbox, so the adb side is a fake adb that
prints the same mDNS, pair, connect and install output a phone/adb would; the
QR side is checked independently against `qrencode`, `ZXingReader` (zxing-cpp)
and the harness's own encoder.  The terminal captures are of the real
`tool/qr_install.sh` in a real tty (an Emacs `term` buffer in the worktree's dev
harness, photographed with `scripts/dev.sh shot`, and a pty driven by a script),
not mock-ups.

## The report: a plain run no longer showed a QR code

> why doesnt qr install show a qr code anymore? qr code pair is an option in adb

A plain `tool/qr_install.sh` printed the *Pair device with pairing code*
instructions and a `Six-digit pairing code shown on the phone:` prompt, and
never drew a QR code (this is the script as it was at `HEAD`, run against the
same fake adb):

```text
On the phone:
  Settings -> System -> Developer options -> Wireless debugging
  -> Pair device with pairing code.

Keep that dialog open.  This computer finds the phone with mDNS, asks for the
six digits, then installs the app.  The phone and this computer must be on the
same network.
Pairing address: 192.168.7.42:37111
Six-digit pairing code shown on the phone:
```

That was deliberate, and it went too far.  The report before this one ("the qr
install script outputs a qr code which makes my phone disconnect from its
current wifi", commit `aea2c83`) was answered by making the six-digit code the
default and putting the QR code behind `--qr`.  But *Pair device with QR code*
is a first-class option of Wireless debugging (Android Studio's pairing dialog
uses it too), and this script is named for it.  The Wi-Fi drop comes from
something else *reading* the code, not from showing it: the scanner behind that
option does not join a network.  Read from the AOSP sources on 2026-10-19
(`packages/apps/Settings` and `frameworks/base`, master):

- `AdbQrcodeScannerFragment` (Wireless debugging > Pair device with QR code)
  parses the scan with `AdbQrCode` and calls `enablePairingByQrCode(ssid,
  preSharedKey)`.  Nothing in it touches Wi-Fi.
- `AdbQrCode` requires the `WIFI:` scheme, `T:ADB`, and a non-empty `S:` and
  `P:`.  There is no length limit on the service name: `WifiNetworkConfig`'s
  validity check only wants it non-empty.
- `AdbDebuggingManager.PairingThread` registers the phone's
  `_adb-tls-pairing._tcp` mDNS service under that name
  (`serviceInfo.setServiceName(mServiceName)`), which is what the script waits
  for in `adb mdns services`.

So what keeps a camera app from using the code is the service name that is
longer than a Wi-Fi SSID; the QR code never had to be taken away.

The fix:

- **A plain run shows the QR code again.**  `--qr` still exists and means the
  same, for anyone who gives it.
- `--code` pairs with the six-digit code instead (the flow the earlier fix
  added).  `--pair-code` and `--pair-address` only make sense there, so they ask
  for it themselves.  `--qr` together with `--code`, `--pair-code` or
  `--pair-address` is refused before anything runs.
- What the earlier fix added stays: the service name is `studio-` plus 32
  random characters (39 bytes), longer than the 32-byte Wi-Fi SSID limit, so a
  camera cannot turn the code into a network; the screen and `--help` say to
  scan from *Wireless debugging*, not with the camera app; the QR is still
  error-correction level L, version 4 (33 modules, 41 with the quiet zone); the
  code is shown on a cleared screen; pairing matches the QR's own service name;
  connect services are restricted to the phone that paired (address or guid);
  refused ports are retried; and `--connect` remains the recovery path.

The new tests are the regression for this report:

- `test_a_plain_run_shows_a_qr_code_to_scan` runs the installer with no pairing
  option and asserts that it draws the QR code (`\033[47;30m` rows), says *Pair
  device with QR code* and warns against the camera app, never asks for six
  digits, pairs with `adb pair 192.168.7.42:37111 PASSWORD`, installs, and that
  the drawn code is exactly the payload built from the service name the phone
  advertises and that same `PASSWORD` (the test renders the payload itself and
  finds those rows in the output).  Run against the script as it was at `HEAD`
  it fails: that script printed the pairing-code instructions and stopped with
  `no pairing code given` (exit 1).
- `test_the_qr_code_can_be_left_to_the_six_digit_code` runs `--code`, types the
  six digits on stdin, and asserts that no QR is drawn and `adb pair ... 123456`
  is what runs.
- `test_qr_and_code_are_not_asked_for_together` covers `--qr --code`,
  `--code --qr`, `--qr --pair-code` and `--qr --pair-address`: each stops with
  an explanation before adb is run at all.
- Tests that relied on the old default now say what they mean:
  `test_explains_when_no_pairing_service_is_found` passes `--code`;
  `test_pairs_and_installs`, `test_pair_address_skips_mdns_discovery` and
  `test_a_wrong_pairing_code_is_explained` give `--pair-code`/`--pair-address`,
  which ask for the code flow themselves; `test_help` checks that the help leads
  with the QR code, names `--code`, and keeps the camera-app warning.

The same payload checked against a transcription of AOSP's `AdbQrCode` rules
(scheme, `T:ADB`, non-empty `S:` and `P:`; my transcription of the Java, not
the real parser) is accepted, and a wrong security type, an empty name or
password, or a non-`WIFI:` text is refused:

refused  WIFI:T:ADB;S:;P:y;;        -> Invalid format

## The `--code` path

`--code` shows no QR code.  A pty run in which the six digits are typed at the
prompt (echo off) with the fake adb requiring `123456`:

```text
$ tool/qr_install.sh --no-build --apk app.apk --code --timeout 30
On the phone:
  Settings -> System -> Developer options -> Wireless debugging
  -> Pair device with pairing code.

Keep that dialog open.  This computer finds the phone with mDNS, asks for the
six digits, then installs the app.  The phone and this computer must be on the
same network.
Pairing address: 192.168.7.42:37111
Six-digit pairing code shown on the phone: 
Pairing with 192.168.7.42:37111 ...
Paired with 192.168.7.42.
Waiting for the phone's debugging port ...
connected to 192.168.7.42:42345
Connected to 192.168.7.42:42345.
Installing app.apk on 192.168.7.42:42345 ...
Installed.
Opened Harness on the phone.
```

The fake adb saw `pair 192.168.7.42:37111 123456`; no `WIFI:T:ADB` text and no
QR escape was written.  `verification/qr-install-code.png` is the same flow
(`--pair-code 123456`, which asks for it too) in a terminal.

The options that contradict each other stop at once:

```text
$ tool/qr_install.sh --qr --code
qr_install: --qr and --code are different ways to pair; give only one
$ tool/qr_install.sh --qr --pair-code 123456
qr_install: --qr pairs by scanning a QR code; --pair-code and --pair-address are for pairing with the six-digit code (--code)
$ tool/qr_install.sh --pair-address 192.168.7.42:37111 --qr
qr_install: --qr pairs by scanning a QR code; --pair-code and --pair-address are for pairing with the six-digit code (--code)
```

All three exit with status 1 and nothing is drawn or paired.

## The `--serve` branch

`verification/qr-install-serve.png` is `serve_apk.py` with `--address
192.168.7.42` and a fake APK; `zxing-cpp` decodes its code to the download
URL:

```text
QRCode http://192.168.7.42:34281/Harness.apk
```

`ServeApkTest` also exercises the APK response
(`application/vnd.android.package-archive`, `Content-Disposition`), the
landing page, and 404s.  `--serve` clears the screen for its code and opens the
same large image, unless `--no-image` is given.

## The encoder matches the harness's own

The encoder is a port of `harness-ui-qr.el`'s (`harness-qr-encode`).  A batch
Emacs encoded 100 cases (26 strings, including UTF-8 and the pairing payload,
at L/M/Q/H); all 100 matched the Python encoder in version, chosen mask and
every module.

```text
ok 100 bad 0
```

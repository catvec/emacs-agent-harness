# QR phone installer verification

Run on 2026-10-18 from `harness_client` in the task worktree.  No phone or
Android SDK is visible to this sandbox, so the adb side is a fake adb that
prints the same mDNS, pair, connect and install output a phone/adb would; the
QR side is checked independently against `qrencode` and the harness's own
encoder.

## The failure this fixes

The first real run (in an Emacs `vterm` buffer) paired with `192.168.1.119`
and then reported:

```text
Paired with 192.168.1.119.
qr_install: could not connect to 192.168.1.117:46037: failed to connect to '192.168.1.117:46037': Connection refused
```

`192.168.1.117` was a different device's stale `_adb-tls-connect._tcp`
record.  The phone's own record on `192.168.1.119` had not appeared yet, and
the old fallback took *any* connect service, tried it once and exited.  The
same run also showed the QR problem: each attempt printed a new code under the
previous one, and the `.....` progress line kept growing and scrolling the
screen while the phone was pointed at it.

The fixes:

- The code is drawn on a cleared screen (only in a real terminal), at error
  correction level L (version 4 for the 68-byte pairing text, 41 modules with
  the quiet zone) instead of M (version 5, 45 modules).
- The progress is one line overwritten in place with `\r`, so it never scrolls
  the code away; nothing prints the old dots anymore.
- On a desktop a large copy (about 800 px, 20 px per module) opens in `feh`
  (or the default viewer through `xdg-open`); `--no-image` keeps it text-only.
- Pairing uses the service name the QR asked the phone to publish, not the
  first `_adb-tls-pairing._tcp` record (a pairing-code dialog can leave one
  behind).
- `adb pair`'s `[guid=...]` is kept.  Connect services are tried only on the
  address that paired, preferring the guid.  A refused connection is retried
  for the whole timeout, and an `adb devices` serial is accepted only when it
  carries that address or guid.  The old fallback to another host is gone.
- If the port never appears, the error tells the user to read the phone's
  *Wireless debugging* IP and port and run `--connect IP:PORT`, which is now an
  option; it skips pairing and connects directly.

`test_ignores_connect_service_of_another_host` is the exact regression: the
fake advertises `192.168.1.117:46037` while the phone is paired at
`192.168.1.119`, and the phone's port appears a few seconds later.  The test
asserts the run succeeds and that **no** `connect 192.168.1.117` call was
made.  `test_retries_a_stale_port_on_the_same_host` advertises
`192.168.1.119:46037` first, refuses it, then publishes `:42345`; the run
retries and installs.  `test_explains_when_the_debugging_port_does_not_open`
checks the `--connect IP:PORT` advice and again that the foreign host is never
tried.  `test_pairing_skips_another_pairing_server` puts a stale pairing-code
dialog service first and checks `adb pair` is only sent to the QR's own name.

`test_symbols_match_qrencode` encodes every test string at L, M, Q and H and
checks that qrencode's symbol equals one of the eight masks this encoder
produces; `test_largest_version` does the same at version 40.
`test_ansi_render` decodes the printed half blocks back into modules and
compares them with the matrix, so a shifted or reused row fails.
`test_png_dimensions_and_pixels` checks the PNG header and the quiet zone and
finder pixels; `test_large_image_uses_a_viewer` starts a fake `feh` and checks
it is asked to show the generated file.

Emacs encoded 100 cases (26 strings, including UTF-8 and the 69-byte pairing

## A full install, with a fake adb

`--apk` points at a stand-in file so no Gradle build is needed; the fake adb
advertises a pairing service, accepts the password from the QR, advertises the
debug port, and reports the install.  This run also advertises a stale connect
service on `192.168.1.117`, the host from the real failure:

```text

    FAKE_PHONE_IP=192.168.1.119 tool/qr_install.sh --no-build --apk .../app.apk \
    --timeout 10 --no-image
```

## The codes decode

The terminal output from the successful PTY run was rendered to a PNG with
solid terminal cells (the same grid the real vterm shows).  `zxing-cpp` reads
`qr-install-scan.png` and `qr-install.png` as the exact pairing text:

```text
QRCode WIFI:T:ADB;S:ADB_WIFI_ikU3jbKOMgO7vC-ViSSWk;P:hGavpxs2VUYtwfB5L8oax;;
```

`qr-install-scan.png` is the cleared screen during the wait: instruction,
the 41-wide code, and the single `Waiting for the phone to scan the code ...`
line below it.  `qr-install.png` is the same screen after the fake phone
paired at `192.168.1.119`, connected to `:42345`, installed and launched.  The
pairing text is a stale, single-use code; it is only an artifact.

The PNG written by `qr_terminal.py --png` (and opened by `--open`) was
decoded the same way at 820×820 (20 px per module, 41 modules including the
quiet zone) to the same text; `verification/qr-install-large.png` is that
image.

## The `--serve` branch

`verification/qr-install-serve.png` is `serve_apk.py` with `--address
192.168.7.42` and a fake APK; `zxing-cpp` decodes its code to the download
URL:

```text
QRCode http://192.168.7.42:34281/Harness.apk
```

`ServeApkTest` also exercises the APK response
(`application/vnd.android.package-archive`, `Content-Disposition`), the
landing page, and 404s.  `--serve` now clears the screen for its code too and
opens the same large image, unless `--no-image` is given.

# Phone installer verification

Run on 2026-10-19 from `harness_client` in the task worktree.  No phone or
Android SDK is visible to this sandbox, so the adb side is a fake adb that
prints the same mDNS, pair, connect and install output a phone/adb would; the
QR side is checked independently against `qrencode`, `zxing-cpp` and the
harness's own encoder.

## The failure this fixes

The installer used to show only the Android wireless-debugging QR code:

```text
WIFI:T:ADB;S:ADB_WIFI_...;P:...;;
```

That is a Wi-Fi QR code by design: `S:` carries an mDNS service name and `P:`
the pairing password, but Android's camera/QR stack can also read it as a Wi-Fi
network called `ADB_WIFI_...` and a network password.  Scanning it with a
camera (rather than *Wireless debugging -> Pair device with QR code*) makes the
phone leave its current Wi-Fi to join that network.

The fixes:

- **The default flow no longer sends a QR code.**  It pairs with the six-digit
  code from *Wireless debugging -> Pair device with pairing code*: the script
  finds the phone's `_adb-tls-pairing._tcp` service over mDNS, asks for the six
  digits, and runs `adb pair ADDRESS CODE`.  No Wi-Fi credential is ever shown
  or scanned.  `--pair-address IP:PORT` and `--pair-code CODE` allow a
  non-interactive run or bypass mDNS.
- `--qr` keeps the one-scan flow but makes the code unusable as a Wi-Fi
  network.  The service name is now `studio-` plus 32 random characters (39
  bytes): longer than the 32-byte Wi-Fi SSID limit, so a camera cannot join it,
  but still a valid mDNS instance name (63 bytes) that the wireless-debugging
  scanner passes through.  The screen also warns to scan it from *Wireless
  debugging*, not with the camera app.
- The QR is still error-correction level L, version 4 (33 modules, 41 with the
  quiet zone), so it stays as easy to scan as before.
- The earlier fixes are kept: the code is shown on a cleared screen, the
  progress is one overwritten line, pairing matches the QR's own service name,
  connect services are restricted to the phone that paired (address or guid),
  refused ports are retried, and `--connect` remains the recovery path.

## A full install with the pairing code (the default)

`--apk` points at a stand-in file so no Gradle build is needed.  The fake adb
advertises the phone's `_adb-tls-pairing._tcp` service, accepts the six-digit
code, advertises the debug port, and reports the install:

```text
$ FAKE_ADB_STATE=... ADB=.../adb FAKE_PHONE_IP=192.168.7.42 \
    FAKE_PAIR_CODE=123456 tool/qr_install.sh --no-build --apk .../app.apk \
    --pair-code 123456 --timeout 10

On the phone:
  Settings -> System -> Developer options -> Wireless debugging
  -> Pair device with pairing code.

Keep that dialog open.  This computer finds the phone with mDNS, asks for the
six digits, then installs the app.  The phone and this computer must be on the
same network.
Pairing address: 192.168.7.42:37111
Pairing with 192.168.7.42:37111 ...
Paired with 192.168.7.42.
Waiting for the phone's debugging port ...
connected to 192.168.7.42:42345
Connected to 192.168.7.42:42345.
Installing app.apk on 192.168.7.42:42345 ...
Installed.
Opened Harness on the phone.

Harness is on the phone.  In the app, connect to the harness's ws:// address
(Emacs: C-c h P, [start serving]) and its token from acp-token.
For hot reload while the phone is connected: tool/flutter run -d 192.168.7.42:42345
```

The fake adb calls were:

```text
devices
mdns services
mdns services
pair 192.168.7.42:37111 123456
devices
mdns services
connect 192.168.7.42:42345

-s 192.168.7.42:42345 install -r .../app.apk
-s 192.168.7.42:42345 shell am start -W -n app.harness.client/app.harness.harness_client.MainActivity
```

No `WIFI:T:ADB` text and no QR escape was written; `verification/qr-install-code.png`
is this run in a terminal.  The interactive variant (no `--pair-code`) prompts
`Six-digit pairing code shown on the phone:` and reads the six digits with
echoing off; feeding `123456` to the same fake adb pairs and installs.

## The `--qr` path

The QR still pairs, now with a 39-byte service name.  A PTY run with the fake
adb's pairing service delayed by two polls produced:

```text
Wireless debugging > Pair device with QR code
Scan it there, not with the camera app: a camera reads it as a Wi-Fi network.

[QR code, 41 modules wide including its 4-module quiet zone]

Paired with 192.168.7.42.
Waiting for the phone's debugging port ...
connected to 192.168.7.42:42345
Connected to 192.168.7.42:42345.
Installing app.apk on 192.168.7.42:42345 ...
Installed.
Opened Harness on the phone.
```

The generated credentials in that run were 39 and 21 bytes:

```text
studio-77sM9ebmiUvjoiyZGfUy8wP7wM5Kw7Z3 UnZPwUlMQECFYJDD1eEC3
```

`verification/qr-install.png` is the finished screen; `zxing-cpp` reads its QR
as:

```text
QRCode WIFI:T:ADB;S:studio-77sM9ebmiUvjoiyZGfUy8wP7wM5Kw7Z3;P:UnZPwUlMQECFYJDD1eEC3;;
```

The scan-time capture, `verification/qr-install-scan.png`, is the same screen
with a different generated code and decodes to:

```text
QRCode WIFI:T:ADB;S:studio-QRtLXYl6qN83OHsfZ2WotKHEc8h0kyEW;P:IfB9r5diwsOUYFKZS3rwx;;
```

`verification/qr-install-large.png` is the 820×820 PNG that `--open` shows (20
pixels per module); it decodes to the same 39-byte/21-byte pairing text.

The QR text is a stale, single-use pairing code; it is only an artifact.  The
service name is longer than a Wi-Fi SSID, so a camera cannot turn it into a
network to join.  The wireless-debugging scanner does not limit the service
name to 32 bytes (AOSP's `AdbQrCode` passes `S:` to `NsdManager`, whose instance
names may be 63 bytes), so pairing still works.

## The `--serve` branch

`verification/qr-install-serve.png` is `serve_apk.py` with `--address
192.168.7.42` and a fake APK; `zxing-cpp` decodes its code to the download
URL:

```text
QRCode http://192.168.7.42:34281/Harness.apk
```

`ServeApkTest` also exercises the APK response
(`application/vnd.android.package-archive`, `Content-Disposition`), the
landing page, and 404s.  `--serve` clears the screen for its code and opens the
same large image, unless `--no-image` is given.

## The encoder matches the harness's own

The encoder is a port of `harness-ui-qr.el`'s (`harness-qr-encode`).  A batch
Emacs encoded 100 cases (26 strings, including UTF-8 and the pairing payload,
at L/M/Q/H); all 100 matched the Python encoder in version, chosen mask and
every module.

```text
ok 100 bad 0
```

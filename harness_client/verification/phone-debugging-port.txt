Phone debugging port: "stuck waiting" after pairing
====================================================

The report: "i paired w qr code but now it is stuck waiting for phone's
debugging port".  tool/qr_install.sh printed "Paired with 192.168.1.119." and
then "Waiting for the phone's debugging port ..." counting up until --timeout,
and gave up saying the port did not open.  (Earlier changes to this wait made it
ignore a foreign host's service and retry a refused port, e8c4c3e; neither could
help here, because the live service never reached the code that connects.)

The phone's own listing
-----------------------

`adb mdns services` on the machine the script ran on (adb 37.0.0; a query of
the running adb server's mDNS cache, nothing changed; the phone's serial is
masked, <TAB> is a tab):

    List of discovered mdns services
    adb-SERIAL12345-LXX5ft<TAB>_adb-tls-connect._tcp<TAB>192.168.1.119:46037
    adb-SERIAL12345-LXX5ft (2)<TAB>_adb-tls-connect._tcp<TAB>192.168.1.119:39131
    

adb prints each service as "%s\t%s\t%s:%u" (name, type, address:port; checked in
adb's client/transport_mdns.cpp and client/mdnsresponder_client.cpp, and `adb
devices` is "serial<TAB>state" the same way).  The name is free text.  When the
phone registers a name that is still taken, Android renames it "NAME (2)": the
live service here is "adb-SERIAL12345-LXX5ft (2)", beside the old record of the
plain name.  What each of those ports does when connected to (a plain TCP
connect from this machine; adb's state is not touched):

    46037 refused (Connection refused)  <- the old record
    39131 accepts the connection  <- the live debugging port

The bug
-------

qr_install.sh read these lines with awk's default field splitting, which splits
at every space, so "adb-SERIAL12345-LXX5ft (2)" became two fields, "(2)" landed
where the service type should be, and the row was dropped as "not a connect
service".  Only the old record, on the closed port, was left:

  before (the script's mdns_rows):
    adb-SERIAL12345-LXX5ft<TAB>_adb-tls-connect._tcp<TAB>192.168.1.119:46037
  after (split at tabs only):
    adb-SERIAL12345-LXX5ft<TAB>_adb-tls-connect._tcp<TAB>192.168.1.119:46037
    adb-SERIAL12345-LXX5ft (2)<TAB>_adb-tls-connect._tcp<TAB>192.168.1.119:39131

So the script retried the closed port until it timed out, while the live one was
never tried.  adb's own connect right after `adb pair` cannot rescue it: it
matches the instance name exactly (adb_secure_connect_by_service_name), and the
auto-connect on discovery needs the instance name in adb's keystore, which the
renamed one is not; `adb devices` stayed empty.

The same split dropped a renamed pairing service (the QR flow), and a device
adb lists under such a name ("adb-...(2)._adb-tls-connect._tcp<TAB>device").

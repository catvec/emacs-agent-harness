Two delivery defects were found and fixed in the wrapper, and neither
fix made the runs complete
-------------------------------------------------------------
1. The first wrapper redirected `scripts/test.sh` into a file and wrote
   its heartbeat to that file only, so the job's own stdout was empty
   from the start.  `scripts/test.sh` prints nothing until every suite
   has finished: its `say` calls come after the final `wait`, so the
   run itself cannot supply a heartbeat.  The heartbeat now goes to
   stdout.
2. The second piped the run through `tee`.  `scripts/test.sh`'s own
   header records that a batch Emacs leaves SIGPIPE fatal and that a
   write racing the death of a reader kills a suite.  The run's stdout
   is now a file, with no pipe in it.

Both are real defects and both are fixed.  Neither is shown to be the
cause of the terminal outcomes, and `a6ff03` -- which had neither
problem -- ended the same way.

The cause: a suite signals its own process group
------------------------------------------------

It was never the job runtime, the frame reader, memory, or a wall-clock
limit.  The sandbox's supervisor starts each command as

  HARNESS_RUN=$token timeout --signal=TERM --kill-after=3s <secs>s bash cmd

and `timeout` does not make a new session, so `scripts/test.sh`, its suite
shells and the wrapper's heartbeat loop are all in that one process group.
A suite that signals its process group on the way out -- the kind of
cleanup a suite does when it wants to be sure no child of its survives --
reaches the runner and the job's own shell, and both die with exit 143
(SIGTERM).  That is exactly what was observed: exit 143, no recorded stop
request, and ticks arriving normally right up to the end.

Why it looked like a delivery failure
-------------------------------------

The tickers that "stopped reaching the harness" had not stopped producing
output; their whole process group had been signalled, so they stopped
existing.  `a6ff03` looked decisive -- a ticker with no test suite, ending
the same way -- but it too was a child in the same process group, so it was
never an independent control.  The frame-reader theory came from reading
`dd bs=384 count=1` in the supervisor, and it is real but irrelevant: a
group signal ends a run whether or not frames flow.

What makes a run complete
-------------------------

Start the run in a session of its own, so a suite's group signal cannot
reach the runner or the job:

  setsid bash -c 'cd "$ROOT" && HARNESS_TEST_JOBS=4 scripts/test.sh' &

That completed in 625 s at 4 at a time on the committed head, and in
390 s on the commit before it.  On a loaded machine (load 6 to 35 from
other work) the suites at their default nice 19 run slowly enough that
the run outlives the job's frame lease, so `HARNESS_TEST_NICE=0` is what
lets it finish there.  The same
run at 8 at a time also completed (244 s) but failed three suites --
`harness-tools-agent`,
`harness-ui-chat` and `harness-ui-patch-review` -- each of which passes
alone and all three of which pass together at 4 at a time (90 s, 0 failed).
They are concurrency-sensitive, not branch defects: none of the three
modules is touched by this branch.  4 at a time is the setting that passes.

ADDENDUM 2026-11-18: a suite that fails only just after midnight
----------------------------------------------------------------------------

Running the full suite between 00:00 and 00:30 local time fails
`harness-ui-chat` on tests that have nothing to do with this branch.
This is a defect in the test, it is on `main`, and this branch does not
touch `lisp/ui/harness-ui-chat.el` or its test.

What it is.  Three tests in `harness-ui-chat-test.el` build their
timestamps from `(float-time)` and subtract half an hour or more:

  line 11653  timestamps-group-messages-sent-near-each-other
  line 11706  timestamps-pin-the-time-of-the-first-message-seen
  line 11811  timestamps-a-run-of-calls-keeps-its-first-time

Each then expects `harness-chat--time-label` to render that time as a
clock.  The label renders a clock only for today; for another day it
renders `%b %-d %H:%M`, and for another year `%Y-%m-%d %H:%M`
(`harness-ui-chat.el:1539`).  Within the first half hour after midnight,
`now - 1800` is *yesterday*, so the label gains a day and the
expectation is wrong.  Measured at 00:09 on 2026-11-18:

  now=2026-11-18 00:09
  t1 =2026-11-17 23:39
  label(now)=00:09
  label(t1) =Nov 17 23:39
  same day? nil

Two of the three failed in a full run at 00:21; the third passed because
its first timestamp still fell inside the group window it checks.  The
same two fail when the suite is run alone at that hour, so this is not
concurrency and not load.

What it is not.  `harness-ui-pet` failed in the same run on
`harness-ui-pet-board-recaps-its-tasks`, which uses
`harness-test-with-clock` and five-second waits; it passes alone
(56 of 56, 30 s).  That one is load-sensitive and is unrelated.

Consequence for this record.  The full run recorded above was made at
23:38 and is a genuine pass.  A run made in the half hour after
midnight is expected to fail `harness-ui-chat` for this reason alone
until the three tests are made independent of the wall clock -- for
instance by building their times from a fixed local noon, or by
expecting whatever `harness-chat--time-label` itself returns.  That fix
belongs to the module's owner, not to this task.

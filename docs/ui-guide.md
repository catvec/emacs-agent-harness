# Presentation layer guide

UI modules live in `lisp/ui/`, require only `harness-core`,
`harness-util`, `harness-acp` and `harness-ui` (plus each other where
noted), and talk to the harness exclusively through the ACP connection
held by `harness-ui`.  Never `require` a state module and never call a
`session/…` bus method directly: the same code must work against a
remote harness.

## What `harness-ui` gives you

Connection and requests

- `(harness-ui-request METHOD PARAMS)` → promise; `(harness-ui-call METHOD PARAMS CALLBACK &optional ON-ERROR)` for the common case; `(harness-ui-notify METHOD PARAMS)`.
- Extension methods are `"_harness/NAME"` with params keyed by the bus method's argument names, e.g. `("_harness/session/nodes" (:id SID :opts (:limit 50)))`, `("_harness/session/update" (:id SID :name "x"))`, `("_harness/agent/cancel" (:session-id SID))`.  Fork at a node with `("_harness/session/fork" (:id SID :kind "fork" :node NODE-ID))`, never by moving SID's head there and back: the fork, and a checkout (`_harness/session/set-head`), rewind what the model knows to that node, and a head moved under a running turn would have the turn write after it.
- Standard ACP: `session/new {cwd}`, `session/prompt {sessionId prompt}`, `session/cancel`, `session/set_mode`, `session/set_model`, `session/load`.
- Settings: `("_harness/config/describe" (:cwd DIR))` describes every harness option, `("_harness/config/set" (:key "harness-model" :value "\"demo:x\"" :printed t :scope "project" :cwd DIR))` and `_harness/config/unset` change one.  Each setting carries a `:section` (`sessions`, `safety`, `tasks`, `notifications`, `services`) or nil for an advanced one, and the answer's `:sections` lists the sections that have settings, in order, so a client can lead with the common ones.  Values and customize types travel printed (`prin1`, read them back with `read`), so symbols, lists and nil survive JSON; `harness-ui-config` edits them with `wid-edit` widgets built from the types.

Incoming traffic (add named functions to these lists)

- `harness-ui-update-functions` `(SESSION-ID UPDATE)` for every `session/update`; `(plist-get UPDATE :sessionUpdate)` is one of `agent_message_chunk`, `agent_thought_chunk`, `user_message_chunk`, `tool_call`, `tool_call_update`, `plan`, `current_mode_update`, `_harness/node` (`:node` is a full node plist), `_harness/session` (`:session`), `_harness/hint`, `_harness/session_deleted`, `_harness/activity` (`:activity`: what the running turn does now, nil once it ends; `("_harness/agent/activity" (:session-id SID))` fetches it for a view opened mid-turn).
- `harness-ui-event-functions` `(EVENT ARGS)` for `_harness/event`: `agent/turn-started`, `agent/turn-ended`, `session/queue-changed`, `session/pending-changed`, `session/status`, `agent/quota`, `usage/budget-warning`, `merge/queued`, `merge/finished`, `config/changed`, `harness/reloaded`, …
- `harness-ui-quota-functions` `(PROVIDER QUOTA)` after a provider's cached billing and plan quota change: the `provider/quota-updated` event, or a fetch.
- `harness-ui-permission-functions` and `harness-ui-question-functions` `(PARAMS RESPOND)`: return non-nil to own the request; call `RESPOND` with `(:outcome (:outcome "selected" :optionId ID))` / `(:answer STRING)`. A permission request about paths carries the glob pattern it is answered for in `(plist-get (plist-get PARAMS :_harness) :pattern)`, by default everything in the directory of its paths (`DIR/**`); to answer for another one, more or less specific, add `:_harness (:pattern PATTERN)` next to `:outcome` (the chat's `e` on the panel and `C-c C-p` do). The `ui-pending` module owns them when a buffer draws the session (its `harness-ui-pending-drawn-predicates`, which the chat joins), holding them per session and drawing, keying and answering their panels; add your own predicate when another kind of buffer should own them. When nothing owns one, the UI never prompts: it declines, the request stays pending on the session, which then reads as needing input, and its chat panel, popout or task card answers it later. A question's PARAMS carry `:question`, `:options` (the answers' labels) and, when the options have diagrams, `:diagrams`, one per option: `(:type "ascii" :text TEXT)` or `(:type "image" :path PATH :mime MIME)`; the chat shows them one at a time, in one area under the options. `RESPOND` answers on the connection the request came on and returns nil when it could not go out. A view that keeps it for later answers through `_harness/permission/answer` or `_harness/question/answer` once the UI has connected again (`harness-connect-remote`), as the pending module does: the harness never hears an answer sent where the request came, and the session would otherwise stay blocked.
- Requests the UI was waiting on when it connected again are rejected, and `harness-ui-connection-replaced-p` is non-nil for those errors. Do not report them as failures: the harness goes on with them.
- `harness-ui-notification-functions` `(NOTIFICATION)` when the user clicks a desktop notification the UI showed for `_harness/client/notify`: NOTIFICATION is its wire plist (`:title :body :urgency :source :kind :session :task :project`); return non-nil once you have shown what it is about (the task board opens on `:task`). When none does, its `:session` opens.
- `harness-ui-sessions-changed-hook`, `harness-ui-redraw-hook` (reload/reconnect: rebuild your buffers from scratch).

Session cache and context

- `(harness-ui-session ID)`, `(harness-ui-sessions &optional PRED)`, `(harness-ui-refresh-sessions CB)`, `(harness-ui-read-session PROMPT)`.
- `harness-ui-session-id` is buffer-local; `(harness-ui-current-session-id)`.
- Billing and plan quota: `(harness-ui-quota PROVIDER)` (`provider/quota`'s plist, cached), `(harness-ui-refresh-quotas &optional REFRESH)`, `(harness-ui-session-billing SESSION)` (`api`, `subscription`, `extra-usage` or nil), `(harness-ui-format-spend SESSION &optional WITH-QUOTA)` (a price when billed per token, the plan's name such as `Max` when a subscription pays, with the details in its tooltip), `harness-ui-format-window`, `harness-ui-describe-window`, `harness-ui-format-reset`.  Show a session's cost through `harness-ui-format-spend`, never `harness-format-cost` of `:cost` alone: a subscription session costs nothing per token.
- Wire shape: enum values are strings (`"idle"`, `"running"`, `"blocked"`, `"inactive"`, `"ask"`, …), lists are lists, plists are plists, `:false` is false.

Display

- `(harness-ui-display-session ID &optional POSITION)` and `(harness-ui-display-buffer BUFFER POSITION)`; positions `right`, `left`, `bottom`, `full`, `other`; one session per position.  The chat module sets `harness-ui-open-session-function`.
- Faces: `harness-user-face`, `harness-agent-face`, `harness-tool-face`, `harness-tool-error-face` (the call ran and failed), `harness-tool-denied-face` (the permission system refused it), `harness-tool-title-face`, `harness-tool-subject-face`, `harness-thinking-face`, `harness-hint-face`, `harness-summary-face`, `harness-dim-face`, `harness-label-face`, `harness-status-*-face`, `harness-success-face`, `harness-caution-face`, `harness-failure-face` (how something went, see the levels below), `harness-context-*-face`, `harness-queue-face`, `harness-compose-face`, `harness-compose-message-face` and `harness-compose-message-accent-face` (a box that sends to a session, not a new task), `harness-ui-panel-face` (a panel asking the user for something), `harness-ui-key-face`, `harness-ui-output-face`.
- Icons: `(harness-ui-icon 'harness-icon-running)` etc.; `(harness-ui-status-icon STATUS)`.  How something went is marked the way a Japanese table marks it: `(harness-ui-level-icon LEVEL)` is a green circle for `success`, a yellow circle for `caution` (a warning, or work in progress) and a red triangle for `failure`, and `(harness-ui-level-face LEVEL)` colours the word after it ("failed", "denied"); `(harness-ui-tool-level OUTCOME)` maps a tool call's outcome to its level.  Define new icons with `(harness-ui-define-icon NAME FILE SYMBOL TEXT DOC)`: FILE names a monochrome SVG in `icons/` drawn in `currentColor` (so it takes the surrounding face's colour), SYMBOL is the terminal fallback.  Never use emoji, and avoid codepoints with an emoji presentation (▶ ⏸ ⚙ ℹ ⚠ ▪) as symbols.
- Helpers: `(harness-ui-tool-outcome RESULT)` (`denied`, `failed` or `ok` for a tool-result node; tell a refusal from a failure through it, never `:is-error` alone), `harness-ui-format-context`, `harness-ui-model-label`, `(harness-ui-task-title TASK &optional SESSION)` (what a task is called: its session's name once it has one, else its prompt's first line — a session is named after its first turn, so a task at work has none yet), `harness-ui-button`, `harness-ui-mouse-keymap`, `harness-ui-action-button` (a button string running a function, pushed by `harness-ui-action-push`), `harness-ui-kbd`, `harness-ui-add-keymap`, `harness-ui-replace-region` (redraw in place, point and windows anchored), `harness-ui-image-string`, `harness-ui-tool-input-summary`, `harness-format-tokens`, `harness-format-cost`, `harness-relative-time`, `harness-truncate-middle`.
- Fitting a view to its window: `(harness-ui-text-height WINDOW FROM TO LIMIT)` says whether the text from FROM to TO fits LIMIT pixels (exact at the limit, more than it beyond), where `window-text-pixel-size` with a Y-LIMIT cannot tell text that overflows from text that fits.  `(harness-ui-fit-header SEGMENTS &optional WIDTH)` builds a header line of `(TEXT PRIORITY MIN)` segments, dropping the least important and shortening a name with a MIN, so nothing a view keeps for the mouse runs off the edge; every header line is made this way, and a view whose own lines must be one line wide fits them itself (the task board) instead of relying on truncation.
- Tools: name a tool by its label, the name people read ("Read file"), never by the name the model calls it by (`read_file`).  `(harness-ui-fetch-tools)` returns a promise of the table of every tool's spec (`tools/list` without a session, cached per connection; wait for it before the first render, as the chat and the tree do), then `(harness-ui-tool-label NAME)` gives the label, `(harness-ui-tool-title NAME TITLE)` a call's title as people read it ("Read file: x.el", also for titles recorded before tools had labels), and `(harness-ui-tool-title-string NAME TITLE &optional MAX)` the same for a header, the label in `harness-tool-title-face` and the rest in `harness-tool-subject-face`.
- Markdown: `(harness-ui-markdown-render TEXT)` → propertized string (`harness-ui-markdown.el`).
- Keys: add commands to `harness-ui-map` (prefix `C-c h`, `harness-ui-prefix-key`) and entries to the `harness-menu` transient (append with `transient-append-suffix`).
- A view's own commands: list them in its mode's `harness-menu-group` property, `(put 'MODE 'harness-menu-group '(TITLE COLUMN...))` at top level, so a reload updates them (a property rather than a function of `harness-ui`, because `harness-reload` loads the other UI files before `harness-ui.el`).  `harness-menu` opened from a buffer of that mode (or a mode derived from it, or with that minor mode on) then shows the columns under TITLE.  Each COLUMN is a transient group vector `["Heading" (KEY DESCRIPTION COMMAND) ...]`, and the commands run in the buffer with point where it was.  List each command under the key the buffer gives it, so the menu teaches it: a chord such as `C-c C-c` as it is, a plain key behind `.` (`". s"` for a board's `s`), since the menu's own groups own the plain keys.  At runtime the menu leaves out undefined commands, keys its own groups use, and keys a minor mode on in the buffer shows already (minor modes beat the major mode, as in the buffer's keymaps).  `harness-ui-menu-registrations-teach-the-buffers-keys` in `test/harness-ui-test.el` checks every registration against its mode's keymap.
- Pending requests (`harness-ui-pending.el`): one store of what each session waits on, fed by the ACP requests above and by the session's pending list, so a view that is not watching a session can still answer it.  `(harness-ui-pending-items SID)` are the request records, `(harness-ui-pending-summary SESSION)` one line about a session for a card or row, `(harness-ui-pending-status SESSION)` its kind, `(harness-ui-pending-question SID)` the newest question, `(harness-ui-pending-answer-QUESTION SID PID ANSWER)` / `-answer-permission SID PID OPTION` answer, `(harness-ui-pending-insert-panels SID)` draws the panels at point (the chat's tail does), and `(harness-ui-pending-popout SID)` opens or refreshes the popout of them, learning SID's requests from its cached pending list first (`harness-ui-pending-sync-session`), so a view pops out what it shows even when no chat has synced it.  Views that say which session point stands for only need `harness-ui-session-at-point-function`, buffer-local (the session list and the board set it): they then get the shared SPC command, `harness-ui-popout-at-point`, through `harness-ui-popout-at-point-functions`.
- Popout (`harness-ui-popout.el`): `(harness-ui-popout-show KEY TITLE RENDER &rest PROPS)` shows one item of a session or task in a selected bottom side window fitted to it.  KEY (any `equal` value) names the item and reusing it reuses the buffer without running its mode again, so state you keep there buffer-locally survives; TITLE is a string or a function, RENDER draws the content (text-property keymaps win over `q` and `g`), and `:compose` is a function returning SUBMIT `(TEXT ATTACHMENTS)` or nil, called on every draw, which adds the shared compose box under the content.  `harness-ui-popout-refresh`, `-close` and `-buffer` work on a KEY.
- BTW over a view: a view without a session of its own can host BTW side conversations by setting, buffer-locally, `harness-ui-btw-start-function` (a function of the new session's name returning a promise of the session it starts, e.g. through `_harness/task/btw`) and `harness-ui-btw-about` (what the conversation is about, for the hint in the BTW's compose box and its header).  `harness-btw` then starts that instead of a BTW over a session (`_harness/session/btw`), and closing the BTW returns to the view.  Like every BTW, it must be a new session on every call, never an earlier one.  Either way the BTW opens blank in a chat buffer, point in its compose box, and its first message names it.  That buffer is the full chat, header line, keys and menu as any session's.
- Adding to a chat buffer without owning it: `harness-chat-send-functions` `(TEXT ATTACHMENTS)` sees each message sent or queued from its box; `harness-chat-header-functions`, added to buffer-locally with a symbol, returns strings the header line shows in front of the session's own segments (the BTW's [close] and [keep] come from here); the buffer-local `harness-chat-placeholder` says what the empty box asks for.  Never replace a chat buffer's `header-line-format`: that hides its model, permission mode and the rest.
- A panel of your own in a chat buffer: `harness-chat-panel-functions`, buffer-local, returns strings shown between the queue and the compose box, read-only, on every render of the tail (`harness-ui-review` shows a task's review banner this way).  With `harness-chat-send-function` set buffer-locally the compose box means something else there: your function takes its TEXT and ATTACHMENTS instead of the message going to the session (an answer to a waiting question still goes to the question first).
- One item of a session or a task in a window of its own: `harness-ui-popout` gives every popout the same frame -- header line with a title and [close], your `RENDER` function's content (buttons, images and text-property keymaps included), and optionally the shared compose box -- as a selected bottom side window fitted to the content.  `(harness-ui-popout-show KEY TITLE RENDER &rest PROPS)`; one buffer per KEY, reused, its mode not run again, so your buffer-local state survives.  PROP `:compose` is a function returning a SUBMIT function or nil, re-checked on every draw.  `harness-ui-popout-refresh KEY` redraws it (keeping the box's text and point), `harness-ui-popout-close KEY &optional DISCARD` closes it, and `harness-ui-popout-at-point` (SPC on the board) asks `harness-ui-popout-at-point-functions`, in turn, to pop out the item at point.
- Compose box colours: `harness-compose-insert` takes `:face` (the box's background, `harness-compose-face` by default) and `:accent` (the prompt's and the left bar's face).  A host whose box does something else than compose -- the task board's, which sends to an existing session -- passes the message faces, and calls `harness-compose-bar` to carry the same bar onto the lines it draws around the box.  Without either argument the box looks exactly as it did, so a host that composes only messages needs nothing.

## Rules of the house

- Built-in widgets only: `button.el`, `widget.el`, `tabulated-list-mode`, `transient`, `icons.el`, `svg.el`, `image.el`, header and mode lines.  No box-drawing UI except where the medium is a graph.
- Never block: the UI runs in the user's Emacs and the harness in its own process (see "Processes" in architecture.md), so the only way to freeze the user is UI code itself.  Never call the bus (`harness-call`, `harness-method-exists-p`): the modules are not loaded here.  Project roots and file lists come from `harness-files` (`harness-files-project-root`, `harness-files-list` → promise).  Every request is asynchronous; show a lightweight loading state (`harness-dim-face` text, a header-line spinner) and replace it when the result arrives; failures show in the buffer, not just the echo area.
- Every keyboard command has a mouse target: a button, a header-line segment or a mode-line segment with `help-echo`.
- Help text is one line: with tooltips off (`tooltip-mode` nil) it shows in the echo area, where a second line grows the mini window, shrinks every window and moves the button under the mouse, so hovering it makes it hard to click.  Build `help-echo` text from parts through `harness-ui-one-line`, never with newlines.
- Redraw incrementally with markers and `inhibit-read-only`; never re-render the whole transcript on a delta.
- Nothing may overflow its window: a view's lines are fitted to the width, a long list is fitted to the height (the task board holds back its least urgent cards rather than push its compose box out of the window), and a header is built with `harness-ui-fit-header` so its buttons and keys are the last to go.  A view that ends in a compose box measures with `harness-ui-text-height`, never `window-text-pixel-size` with a Y-LIMIT, which reports text that overflows as text that fits.
- Buffers must survive `harness-reload`: keep state in buffer-local variables, rebuild from `harness-ui-redraw-hook`.
- Respect the user's theme: faces inherit from standard faces and specify light/dark variants only for backgrounds.
- A new view, or one that now looks different, gets its README picture taken again: see [screenshots.md](screenshots.md).

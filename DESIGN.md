# Emacs Agent Harness
This is the design document for the Emacs native agent harness. This document describes the indended features and technical architecture of the program.

# Overview
The agentic experience in Emacs as of yet has been well served by generic tools but not specialized to the strengths of Emacs. Additionally Emacs provides a powerful environment in which programs can interact with source code, external programs (shell, build and test systems ect), and use pre-made tools and patterns to complete complex workflows.

The status quo is running a terminal emulator inside Emacs further inside which you run a harness which paints UI elements via curses style drawing commands. Although this gives you access to agentic tooling (Claude code, Pi, ect) it's obviously not an ideal experience (Many layers of indirection between UI, Emacs vterm is okay at best--doesn't compare to ghostty or kitty, curses GUIs aren't great to begin with).

The combination of opportunities to take agentic tooling to the next level with the power of Emacs, and the underserved user experience which sub-par tools like TUI harnesses offer, is what provide an excellent opportunity to make a tool to serve these needs.

# Development Guidance
The first priority is to develop a workflow (set of tools, skills, docs, ect) which facilitate a closed loop hands on development cycle. An Emacs instance should be launched which can be manipulated and inspected / screenshot so that the agent can verify live that the code is working as intended. The code simply appearing implemented is not enough.

It is very important to verify features as they are created. You should not create multiple features without testing each one before going on to the next.

The architecture of this project is such that all modules should be developable in parallel once the core loader logic and API contracts are defined.

Make sure both local emacs and remote client ACP are tested whenever new feature are added or when verifying functionality. 

Since there will be many rounds of human feedback and interation even after your testing it should be safe and easy to reload the harness. This means if new harness code has an error and doesn't compile (if that's needed) or doesn't pass muster in some way it doesn't brick any existing sessions. Since we will be dogfooding the harness to develop the harness. After new code is verified it should be hot-reloaded into the current Emacs instance and all sessions via built in Emacs methods. Also redraw session buffers so if render bugs occured and were fixed they will work now.

# Technical Architecture
The architecture of this harness is inspired by the Pi coding agent, and other modular systems like very mod-able games, D-Bus + XDG + the whole linux desktop system, ect. The core of the harness should be entirely focused on loading modules and facilitating communication between modules. All functionality should be provided via addon modules (even if they are shipped in tree), a plain harness running with no modules shouldn't even show a UI or call a completion API. Different modules need to be able to communicate with the APIs of other modules. This includes making direct calls to enact an action, but also hooking into events which are caused by a module (ex., on question ask). 

> Lesson Learned: Pi's biggest architectural failure is not solving for the D-Bus problem of having many different services with many different API surfaces and events. Plugins never played nice with each other unless the plugins in question were custom made to work with other plugins. 

Typical concerns should be made like any user interface or business logic containing program. The business logic, state, and user interface should all be completely separate systems. They should have clearly defined boundaries (litnus test: can a module be easily tested without the presence of any of the other modules and without extensive mocks).

Broadly the systems from top (closest to user) to bottom are:

- Presentation 
- State 
- Completion provider 
- Tool calls

All implementation must follow Emacs and elisp best practices. Code should avoid running on the main UI thread by any means necessary, responsiveness is a top priority. Use built in Emacs functionality when available and allow for users to configure and customize the harness just like any other piece of standard Emacs functionality.

The separation of presentation and state allows the harness to facilitate remote control of sessions. This should be done over an implementation of the Agent Client Protocol (ACP). This protocol should be used to communicate between the state / business layer and the presentation layer. The Emacs UI is simply a client talking ACP to the core of the harness. Make sure that all pieces of functionality can be exercised via the ACP. Make sure that the implementation of the ACP is Emacs optimized and does not slow down the harness nor the Emacs main UI thread. Over ACP the harness should feel snappy. This could be done via different transport mechanisms (for real servers use TCP messages and JSON, but for local maybe no server and just send lisp objects which are ACP messages directly to a callback handler function).

# User Experience 
The user experience of the harness must be amazing and designed with great care.

- Minimal elegance: Choose what information will be shown on the UI and display it stylishly, choose specific user stories and serve them well with simple but powerful workflows, design as few number of features as possible which can be composed together to service multiple complex patterns
- Always user built in Emacs UI tools, do not settle for using ASCII or UTF-8 tricks to create the UI which is needed
- Responsiveness is a priority: Use UI pattnerns which make the harness feel snappy and quick, if an operation is going to take more than an instant show a loading state while it occurs and then show if it was a success or failure
- Every action with a keyboard shortcut should have a place in the UI where you can click with your mouse to perform the same action
- Polished to an extreme degree: seemless feeling to use like if apple designed a harness, subtle flourishes and good design choices, nothing which overwhelms and ruins the other elegance aspects

# Features
Most features specified here are standard to any agentic harness. 

## Sessions
At the core of any agentic session is a series of messages, and tool calls (from the agent), between the user and an agent. 

- Sessions hold state about a single conversation: current project, its directory, the messages in the conversation, the model, permission mode, number of tokens consumed, total cost
- Sessions can be either active because they are open in the user's harness (even if obscured by another session and running in the background, even when idle) or inactive because the user does not have them active 
- Sessions can be resumed
- Sessions can be forked 
- Sessions are scoped to a specific project (auto-detected) 
- Sessions can move to another working directory, and with it to that directory's project, when the work turns out to be elsewhere: the user moves one with a command, or confirms an agent's request to (it changes the directories the session may reach). A session in a worktree or working on a task stays put, and one running a turn moves when the turn ends.
- Sessions can be idle (waiting for user to send next message), running (agent is generating tokens or ingesting tool calls, ect), blocked (waiting for user response to tool call or for permission)
- Sessions can have a parent child relationship with another session 

## Chat Interface
Session messages should show up like a chat app, where older messages are at the top of the screen and newer messages are at the bottom. The sender and type of the message is identified by the styling of the message (human messages have a slightly lighter background, agent messages use the default background color, agent tool messages have a slightly styled colored background). The chat interface is also where the user can send new chat messages to the agent.

Functional requirements:

- All messages in session are visible in chat UI
- Older messages can be viewed by scrolling up, you can return to newer messages by scrolling down
- The transcript is navigable from the keyboard, without a mouse or a search: point jumps to the next or previous real text message (the user's and the agent's, plans included) past thinking and tool calls, to the next or previous message of the user's alone — the prompt a long session started with included — and to the next or previous tool call or thinking block; a run of tool calls folded under one summary line is a single stop
- Text from all messages is aligned in the user's language direction (english is left to right)
- The sender (agent or user) and type () of a message 
- The sender of a message is identifiable at a glance: user messages open with a "You" name line and a colored bar down their left edge on a slightly lighter background; each agent turn opens with an "Agent" name line on the default background
- A message the user did not write says who sent it instead of "You": "System · SOURCE" for messages the harness sends on its own, such as a task carrying on after a restart, a denied call in non-interactive mode or the merge queue, and "Session · NAME" for another session's agent (`session_send`, a sub-agent's parent), the name opening that session. Their text is muted on a background and bar of their own, so they never read as the user's words; the conversation tree shows a gear or agent icon for them
- If messages are too long they wrap to the next line matching the original line's indentation
- Messages are formatted in Markdown and rendered as such
- A message composition box should be displayed at the bottom of the chat history view
- The message composition box supports multi-lined input, but by default is 1 line, and only expands to a maximum height if the user types a message which spans multiple lines
- History of all messages can contain up to more or more than 1 million tokens, UI must remain responsive and performant with this high amount
- Tool calls from the agent are shown in the correct chronological place in the chat history 
- Tool calls are differentiable from agent and user text messages 
- Tool call messages should show which tool was used, parameters of the tool, and the output of the tool 
- The chat interface should automatically scroll down to show new messages when they arrive, unless the user has explicitly scrolled up and is viewing history in which case do not scroll
- Some models output thinking text which should be visible in a darked text color as to lessen its importance in the conversation
- Non-text messages (like thinking and tools) can be collapsed to just show the name of the tool / summary label, they can be uncollapsed to show details of the tool call and output / thinking text
- Non-text messages can be coalesced into a summary block which indicates what and how many tools / thinking was used, this can be uncollapsed to show the tools in their collapsed state, and further uncollapsed to show tool output, only tools / non-text message types which are on an explicit allow list can be coalesced like this in order to prevent hiding of essential tools which block a session
- The chat interface must be aware of how it opens in Emacs and what position it takes up, presets to open in several convenient places like on the right hand side vertically split
- Only one session must be visible in each position, if a session is already open in a position and a different session must be opened with the same position preset--then that different session should replace the existing session, so that you can switch between sessions
- System hint messages can be shown from the harness to tell the user when harness configuration (like session info: name, model, permission mode, ect) change, the text should be muted like thinking but distinct
- System hint messages about something that changes again and again (like the tool slots following the machine's load) must not fill the chat: the changes of one stretch are kept in one hint, shown as a single collapsed line ("Slots changed due to system load (3 changes)") that can be expanded to show each change
- How such a thing stands now (how many tool slots there are while the machine's load holds them back) is shown pinned above the compose box, like the todo list and the running sub-agents, and only while it is held back, because the hint that told of it stands wherever the first change landed
- Messages from the agent, the user, and thinking / tool messages should all have their contents be searchable

### Image Video Audio Support 
Modern models are multimodal and can declare capabilities such as understanding data in the form of text (common), image, video, and audio. This could include the support of each of those modes on input and / or output. A common configuration for coding agents is text and image input and text output. Especially key is the ability to handle uncommon MIME types in the user's clipboard. If you don't know what it is pass the data and the MIME type all of which are considered somewhat hostile user inputs, to the agent and see what it thinks.

The conversation UI must be able to display images if the Emacs instance is capable. Ideally video is playable in emacs or at least a command to open the video and also do thumbnails w builtin emacs functionality. Audio should also be supported if the model supports it. Allow for audio input and audio output. Have good user interfaces which show what is clearly happening with all these modes (playback bars, volume, audio mic monitoring).

### Queued Messages 
If the agent is mid-turn and the user sends a message, it is delivered as a steering message: the agent injects it into the running turn at the next step boundary. While a tool call or a model stream is in flight the message cannot interrupt immediately, so it is held until that step finishes. A message can also be explicitly queued for the next turn with the Queue button or `C-c C-q`. Queued messages should be shown at the bottom of the chat interface right above the compose message box. Queued messages can be edited before they are sent by selecting the queued message from the queued message list and re-composing it. Queued messages should all be sent at the next possible turn in the session all at once. A queued message is drawn as the message it will be once sent, by the same code, with its state and its buttons beside the user's name; the queued messages come last in the conversation, under them the line saying what a running turn does. A queued message can also be sent on its own, now, with its Send now button, the others staying queued. The UI says in a word which state a message is in, so none looks sent that is not: queued; sent, while a turn runs and the message waits for the model's next step; delivered, once the turn took it and the model has it; or not delivered, when the turn was cancelled before it took it (the next turn reads it).

### File References
Allow user messages to have references to files, who's absolute path and size in bytes will be attached in the user's message. These files are referenced by putting an at symbol followed by the file name. The harness should perform fuzzy searching for files matching the contents after the at symbol.

If the user is in GUI mode of Emacs make use of the operating system drag file on to application behavior to attach that file to the message.

Show attached files near the compose message box, use their relative path to the project root and shorten in the middle if needed, allow via this ui to open that file as a buffer or remove it from the message.

Every attachment puts a reference to itself into the message text where the cursor is, and the reference is shown inline as a chip: an image's `[image 1]`, a file's `@path`, a task's `@task:ID`. They are one kind of chip, since they are all attachments: the same look, and the same click actions (open it, remove it from the message, copy its path). Deleting the reference removes the attachment, and undoing it brings it back.

### Task References
A task of the project can be attached to a message like a file: from the compose box, from the task board's card, or by `@task:` and part of its id. The model is given what it needs to know of the task, as text (its id and title, state, session, branch and prompt) and the task tools to read more.

### Skill References
Allow user messages to have explicit reference to a skill, who's contents will be attached to the user's message.

### Keys of the Panels Above the Compose Box
The question and permission panels, and the task board, offer keys of their own (a question's option numbers, a permission's y and n, F for the fullscreen layout). They work while point is on the panel, and type into the compose box while point is in it. There is one consistent way to aim the next key at a panel from the box, the same for every panel and every view: a prefix key, `C-c .`, and then the key. It presses that key on the nearest panel above the box that has it (a numeric prefix takes the Nth one up) and leaves point and the draft in the box. Each panel says so on a line of its own, and the box's tooltip and the menu name the key. The box's `M-<` and `M->` go to the top and the bottom of the box, not of the buffer; pressed again they go on to the buffer's.

### Prompting With the Region
Selected text starts a message, in any buffer, not only a harness one. In a chat, the task board or a popout it is quoted in the compose box. In any other buffer it goes into the compose box of the project's newest session (or a new one, or one the user chooses) with where it comes from (the file and its lines, or the buffer's name), code in a fenced block and prose as a quote, and the session is shown with the cursor in the box ready for the request.

## Window Positions
Harness buffers open in a set of position presets (right hand side vertically split, left, bottom, full, ect). Sessions are not the only buffers which use these positions, any harness buffer which takes up a good amount of space (session list, task mode, cost and usage overview, ect) shares the same positions as sessions. Only one buffer is visible in each position, opening one of these buffers replaces the session in that position and opening a session replaces the buffer, so that you can switch between them without windows piling up. A rare few small windows should not follow this behavior (ex., the help menu should never replace a session).

## Conversation Tree 
The history of messages, tool calls, ect should be represented as a directed graph. A view should be provided which shows the nodes of this directed graph (only showing a short amount of the content from each message node) so you can navigate back in time and between forks of the conversation. The graph view should mirror a Git representation of commits and and branches.

## Compaction
As a conversation approaches the maximum number of tokens a model can fit in its context window it must be compacted down to a smaller size. Enough headroom must be left in the conversation so that the compaction output can be generated and swapped out for the previous full context. As a conversation approaches the compaction limit start highlighting the token count of the session in progressive warning colors.

A message that reaches a session after its prompt cache lapsed would send the whole conversation again, uncached, whoever sent it: the user coming back, feedback on a task that sat in review, another session's agent, the merge queue. Such a message waits while the session asks what goes first: a brief summary, a summary, a transcript file, a fresh start, carrying on with everything, or not now, each with its cost. Answering "always" with a choice makes it the default and stops the asking; like a lasting permission answer, that answer offers [Undo], which asks again with the earlier default, and then [Redo]. A session that never waits for the user takes the default without asking, and no model judges the choice: the default is the brief summary, which never pays for the whole conversation uncached. Whatever goes first, the conversation compacted away stays searchable by the model (the session_history tool), so a summary that left something out never loses it.

## Session List
View sessions and switch between them.

- Display list of sessions scoped to current project
- Show name of session, all status types, tokens, model
- Show how fast a session writes (its average output rate over its whole life, not the last few calls), the thinking level it runs at and how long ago its last message came
- Filter and sort list by any attribute of session
- Child sessions should be shown in a tree under sessions
- The list is wide, so every column can be hidden, per list, and a couple are hidden to begin with
- Show only the sessions that work on a task (with the children under them)
- The list follows the sessions live, which moves rows under the pointer while a model streams, so the live updates can be paused and resumed

Sessions are marked the way files are marked in Dired, and the list's actions work on every marked session, or on the one at point when none is marked: delete, cancel a turn, deactivate, make a task, the priority. The harness's setting commands (model, thinking level, permission mode, non-interactive mode, supervisor mode) work on the marked sessions in the list exactly as they work on the session of a chat, and also on the tasks those sessions work on. This is how many sessions or tasks are changed at once, so the task board has no mode of its own for it. A session the filters hide stays marked and is acted on with the rest, so the mode line counts every mark, and a delete says how many of the sessions it names the list does not show.

## Session Blocked Notifier
There should be a UI element placed outside of the harness UI to display how many sessions are blocked needing user input or idle or working. This should be visible from any other buffer when there is at least one session active in the current project or any other project (aka if there is an active session in the current emacs instance). The purpose of this indicator is to tell the user when they are needed (either to answer a question / approve something or to direct the agent on to the next task). So it should be a small but noticable and trackable UI element which has in mind the concept that users may be rapidly switching between projects and sessions.

## Session Auto Naming 
If a name is not provided when a session is made (not mandatory) then an agent will be used to name the conversation. This ability can be triggered at any time during the conversation, but it will auto trigger as soon as the first message from the user is sent, alongside the turn rather than after it (a task's first turn can last until the task is done, and its name is its title on the task board). The automatic naming runs the user's first message through a cheap model (the provider's simple tier) in a request of its own, apart from the conversation. A task is named the same way as soon as it is submitted, from its prompt, even while it waits in the queue for a slot, and its session takes that name when the task starts instead of being named again; nothing ever waits for the name. Like the other model calls the harness makes on its own (permission judges, recaps, summaries), naming is independent of the limits on concurrent sessions: it takes no slot of the task board and waits for none, so a queued task is titled all the same, and a request that fails is left to the layers below, as any model call is (a lost connection is tried again there), not to a timer of the task board. Naming triggered later in the conversation is done by forking the conversation using the same model (since the conversation is cached by then). A system hint from the harness should be shown to indicate renaming has started and then when it is done.

## Permissions 
Tool calls should have a permission hook which is responsible for performing some process (be it asking the user, automatically approving due to the tool, or a more advanced decision) to determine if the tool is allowed to run or not. Using this many advanced permission systems can be created. 

An answer that lasts (allow or deny for the session, or always) saves a rule or grants a directory. It is noted in the session's chat, under the call it answered, wherever the answer was given (the chat, a popout, the task board), with an [Undo] that takes back exactly what that answer saved, and not the decision on the call itself. Once undone it offers [Redo], which saves it again, and that [Undo] again. Undo and redo are safe against later edits: a rule changed since (in Settings, say), or saved again by another answer, is left as it is, and the note says so, as it does when the rule is gone already.

A lasting answer says exactly what it allows. A prompt about a call offers a ladder of covers, from the narrowest to the widest: the very call asked about (this command line, these arguments, this file), the programs and subcommands a command runs, the directory or the project a file lies in, and every call of the tool. Each step is worded by what it leaves free ("any arguments", "any path"), so that all calls of a tool and only some arguments of them never read alike, and the answers for the session and for always hold for the step chosen, which the prompt shows in its panel, its tooltips and the note that follows. The prompt starts on what such an answer always held for, or, by a setting, on the narrowest step: least privilege first, and a wider step is a choice made on purpose when the work needs it, such as when the directory jail is in the way. A prompt about a directory outside the allowed ones offers the same ladder as patterns, from the file asked about to the repository holding it.

Such an answer is a lasting decision, and lasting decisions are the harness's, not a session's: one made in one session is undone or redone from any other, and after a restart. Wherever one takes effect later and the chat says so -- a call its rule denied, a cold cache compacted unasked because an "always" answer made that the default -- the message names the decision with the same [Undo] or [Redo], in whichever session it shows.

### Directory Jail
By default session should not be given permission to files outside of the current directory. Enforce this with read, write, search, ect commands. Every session also gets its own directory in tmp, which is on its allow list from the start, so scratch files never need permission nor land in the project. Inspecting the harness itself is one of the powerful things of the harness, so it is never refused: every session may read the harness's code and its state directory (sessions, task boards; never its credentials), and use the tools that inspect sessions, tasks and the user's live Emacs, in every mode and without asking, while writing there stays jailed. Skills are read the same way: every session may read the skills directories (the global ones, the project's, Claude Code's plugins'), bash included, read-only and without asking, so an unattended task never stops on a prompt over a skill; where that does not fit (a link out of a skills directory, a project's or plugin's skills leading out of it, a remote host's skills) the read is refused at once and the agent is pointed to the skill tools, and nobody is asked. If a session wants to add another directory to its allow list the user must give permission. If an automatic tool call deny is required provide constructive information to the agent so it succeeds and doesn't require user intervention to use the correct directories, work with what you have.

### Access, escalation and giving access up
Each session has one view where the user sees everything it may reach and how its calls were judged, and sets it up for a tighter jail than the defaults: the jail (the sandbox backend its commands run in, its permission mode, whether it is interactive, the network, writing), its directories (written, only read, given up), the tools it is offered and why the others are not, its rules, the requests it waits on, and a filterable list of the permission judgements of its calls -- what was decided, by whom, the call's handle -- each call drawn with the chat's own tool-call block, the retry ([Approve]) of a refused one included. What the user changes there takes effect at once. Every sensitive attribute of a session -- a directory, the network, writing, a tool, a more permissive permission mode, non-interactive mode -- is raised only through one escalation request, which only the user can grant: no mode, rule or judge answers it, and a session nobody can answer for is refused. Giving access up is the other way round: an agent may always give up capabilities, directories and the rest, and nobody is asked. A session's sub-agents and forks take its restrictions with them, so it cannot get around what it gave up by starting another.

### Auto Mode
User a cheap LLM to determine if a tool call is allowed. Give the details of the tool call (description as seen by agent) as well as the parameters and any other supporting context. The cheap LLM outputs a decision along with a reason. The judge is a safety check on that one call: it is given the call alone (no conversation, no project instructions such as CLAUDE.md, which it used to enforce as if they were permission rules), it leans to allowing ordinary work, and it refuses only serious, hard-to-undo harm or the agent widening its own permissions. A call it would deny is put to the user in an interactive session, with the judge's reason, so a wrong verdict is a question rather than a wall; only a non-interactive session takes the denial as it stands.

### Non-Interactive Mode 
Using this hook system a mode can be enabled which forces the model to attempt to not get blocked waiting for user input. If enabled and a tool call would be disabled an automatic steering message is sent to the agent telling it that it should do everything in its power to find a different approach which respects the permission denial but also achieves the goal. The user of this mode is for when users start a task and know they will be stepping away for a while and want the session to get work done.

## Completion API
Model providers are generic. There is a set of API methods which model providers must implement in order to provide functionality needed for all the harness's usage. Provide a built in implementation of the OpenAI compatible completion API. Providers can provide extra optional capabilities enable features in the harness (like knowing your plan's quota, if a session is still in the KV cache, dynamic pricing).

### Claude SDK
To support users with subscription plans a completion API provider should be implemented which uses the official Claude Code SDK. This is in line with Anthropic's policy's on how external tools can use Claude.

## Cost Tracking
Each completion API call should be associated with a usage cost. Usage cost should be tracked for the session down to the message. Cost should be tracked across sessions and projects to provide aggregate information. 

### Cost and Usage Overview
A page should exist which shows graphs and stats about model, token, and cost usage broken down by project and other associated dimensions. 

### Budgeting
Budgets can be set on a per-session, per-project, and per time period basis. Budgets can be set as informational or as hard quotas. For time period based budgets planning tools should be provided to split the budget across the time period by days (configurable between business days or all days) or hours.

## Internal Calls
The harness makes model calls of its own, outside any conversation: the permission judge and the Elisp judge, the session judge, a session's name, a recap, the Insights summary, the companion pet and the task board's search. Each is recorded as a session of kind internal, so what it asked, what the model answered, which model it was, how long it took and what it cost can be read like any session, and its cost is counted with the rest. A call made for a session is listed under it. Recording changes nothing about the call itself.

An internal session is a record, not a conversation. Nothing can be sent to it, and it takes no part in what counts sessions or picks them: the mode line notifier, the session pickers, the conversation tree, changes made to many sessions at once and the agent's search over sessions leave it out, and the task board does not reload for it. The session list hides it unless asked. Only the newest are kept (a hundred by default), the oldest that are not running going as new ones start, so these records never pile up.

## Git Worktree Aware 
Sessions can be associated with a git worktree. The session's working directory should be set to the git worktree's directory. The harness should have the ability to manage the worktrees.

## BTW
Allow for side conversations to be quickly started to check on quick informal details about the conversation. Each btw conversation is a brand-new session that shares nothing with the session it was opened from, nor with other btw conversations, even ones opened over the same session; a UI shows it over the current session. This way you can keep your current session running and not leave its output while also seeing the response to a btw conversation and even following up. When you are done this btw conversation can be easily closed and you can return to your main session as if nothing changed. Btw conversations should be listed under the session they were opened from, in the session list and the conversation tree. So that quick questions get quick answers, and cost little, a btw conversation starts at a low thinking effort level and runs on a cheap model (the simple tier of the session's provider), unless the configuration picks another; one btw conversation can be started on a model of the user's choice instead.

## Cache Aware
The harness should use provider APIs to determine when tokens from a conversation are in the KV cache. This applies not only to the cache hit rate of token generation but also awareness of when a conversation's tokens have left a KV cache and replying with a new message would result in entire conversation being run through at full cost again. Workflows should be based around the reality of LLM inference, its auto-regressive nature, and how caching makes it better to fork a session then to start a sub-agent which needs to gather all the context again with new costly tokens. A fork onto a model whose cache does not hold the conversation gets the same care as a session whose cache lapsed: it is compacted before its first turn, as the cold-cache choice would for a session nobody is asked about, rather than reading the whole conversation again at that model's price.

## Fork
A new session can be created using the context and settings of another existing session. This lets new tasks or lines of thought be persued by parallel agents all sharing some initial state. This also leverages the auto-regressive LLM caching price model. Where tokens you already have are better than a fresh context in many cases. Forks should record their parent session and show up on the session list.

## Sub-agents 
Sub-agents should be able to be created by an agent as a tool call. Sub-agents just create a new fully fledged session with the context they are provided. Sub-agents should be able to be viewed using the normal session viewing UI. Sub-agents should have their session parent be recorded. A sub-agent can also be made out of a fork of a conversation if choosen.

## Emacs MCP/Tool
Tools should be provided to the agent to interact with the current Emacs session: view buffers and windows, look up variables and functions, find where they are defined and read their source, trace a function's calls or a variable's changes while the user works, show a buffer or file, insert text, save a buffer, and help the user drive and debug it. They are a fixed vocabulary of bounded operations; none evaluates model-written code in the user's Emacs, save one tool the user can turn off (below).

Like every tool call, these run in the harness (the server), never in a client: an ACP client need not be an Emacs (an app on a phone), and the harness must be able to run headless. The user's Emacs is instead a resource these tools reach, the way the file tools reach a TRAMP host: an Emacs UI lends itself to the harness when it connects, and the tools ask that one Emacs for what they need. With no Emacs lent, they say so and every other tool works. These tools are a fixed, bounded vocabulary -- read buffers, windows, symbols, definitions and *Messages*, show a buffer or file, insert text, save a buffer, trace a function or a variable into *trace-output* -- and none evaluates code: model-written Lisp evaluates in a background Emacs instead, since in the user's Emacs a blocking call would freeze it. The one exception is on by default, and the user can turn it off: a tool evaluates Lisp in the user's Emacs, but only code a judge model expects to return at once, only after the same permission checks as any tool that runs code, and guarded so the code cannot prompt, the user's next key stops it, and it is stopped once it has waited a moment.

## Emacs Native Tools
All operating system modification tools should be implemented using built in Emacs functionality. Common tools like read, write, list, search should all use the built in Emacs tools which a user might use for those workflows. An elisp terminal should also be made available as an alternative for Bash. Additional tools like a bash tool or things not implementable in Emacs are allowed by the first choice is to implement a tool in Emacs. The implementation of a tool in Emacs must be fast and not block the main UI thread.

## TRAMP
The Emacs TRAMP functionality should be supported. A powerful part of Emacs is all the Emacs native workflows for reading, writing, listing, searching, ect files can also take place transparently on another system. This lets you use the power and familiar Emacs tools on remote machines. Tool calls can be configured to act on other hosts this way.

An agent reaches other hosts the same way, never around TRAMP: a session started in a TRAMP directory works on that host, every tool takes a TRAMP path whatever host its session is on, and the ssh tool runs a shell command on a host through a TRAMP directory there, sharing TRAMP's connections and settings. A host is a directory outside the session's like any other, so the user grants it before a tool reaches it. The harness has no terminal, so a host it connects to must need no prompt; when a connection fails, the agent is told why and how the host is set up, rather than left to guess.

## Merge Queue 
Forked sessions can elect to try and submit their changes back to a main session. This is useful in cases where a small bug was found and a git worktree and session fork was spun up to fix the issue. Instead of submitting the change as a formal PR with overhead the changes from the worktree can be merged back into the parent sessions working directory. A queue of sessions who want to merge into a parent session is maintained, and only one session gets access to merge into the parent session at a time (this means the parent session itself may stop at points to allow another session to access its files). If any merge conflicts occur they are resolved in the child's worktree, by default by a fresh session the harness starts for just that (the child may have waited long in the queue, and waking it would pay for its whole context on a cold cache).

One queue, one target. A merge names where it goes, not who asked: the session whose working directory the branch merges into, or the main checkout itself (a directory, the root target, with no session behind it). Both are the same code, the same conflict resolution and the same events, so merges nest at any depth. A task is the plain case: its session works in a worktree, its branch merges into the project's main checkout. A session that delegates to sub-agents is the nested one: each worker gets a worktree of its own and its branch merges into the session that started it, which is itself a worktree on a branch that merges into the main checkout in its turn. Nothing else changes at either level.

Order is built in. A session's branch may be queued upward while its own workers' merges are still to come, but it waits: the queue serves a target's merges in the order the work was built, children first, and a session may not hand in until the merges into its worktree are through. A merge that failed does not block the parent -- that is the child's to fix, and the queue told the session so -- and the queue view shows it.

The session shows its own queue. A session whose branches merge into it lists them above its compose box, beside its todo list: which children are queued, merging or in conflict, and which merged or failed recently, with the reason the queue gave. It follows the merge events, so it is where a user watches parallel work come together, and where a stuck conflict is seen.

## Model Tiers
When the harness picks a model on its own it picks by how hard the work is, from the provider the session is on, so that a session on one provider is never served by another. Every provider names a model for each of four tiers: simple (small, well-specified work, and the harness's own calls: the permission judge, naming, summaries), medium (everyday work: a planned task's work, the steps of a supervisor's plan), hard (the strongest model the harness picks on its own: what a task in Plan mode and a supervisor plan on, and a step retried because its worker was not up to it) and frontier (the very top model, which the harness never picks: only the user does). On Claude they are Haiku, Sonnet, Opus and Fable. A tier can also name the thinking level its model runs at, so a provider with one model makes its tiers of the thinking levels instead: DeepSeek runs Flash at low, high and max thinking for simple, medium and hard, and has no frontier model. A tier a provider does not name is taken from its models by price, and where a provider has no model for a tier the nearest tier it has stands in.

## Actual Linux Jail
For users who want to get very serious with it use a real Linux jail. Isolation is kernel-enforced, not policy-enforced. `harness-sandbox` picks a backend at startup and every tool spawn is routed through it.

- Backends, in preference order: `bwrap`, `systemd-run --user`, `none`.
- Fail closed if a policy requires confinement and no backend is available; warn loudly rather than silently running unconfined.
- Filesystem: read-write session cwd; the skills directories read-only (never one that holds HOME); tmpfs, purposely not HOME or any other files to avoid very valuable files like npm credentials being accessible and minimal system or kernel mounts to prevent breakout or other attempts
- Process: `--unshare-pid --unshare-ipc --unshare-uts --die-with-parent --new-session`.
- Network: allowed by default (hosted providers need their API); `--unshare-net` is opt-in and only correct for local models.
- `:permission-mode` is a prompt-level hint, never a security boundary.
- Scope: only processes the harness spawns. Users launching `claude`/`codex` directly get those CLIs' native sandboxes.

## Task Mode 
Manage sessions by the task they are trying to complete. One session per task. Light touch with the management of the actual session. This mode is ideal when doing full auto mode and you trust the agent to complete tasks. In task mode you see a list of your sessions with status information (idle, ect) as well as what each task a session is completing. There is also a chat interface to submit new tasks, this should be the exact same message composition box sessions use (multi-line input, file references, skill references, attachments, ect) and reuse its implementation instead of duplicating it. This acts as mini kanban board showing tasks which are pending, requires user input, in progress, and completed. You can select a session to fully view it. Tasks are scoped to the current project. 

The task mode should facilitate the full lifecycle from of the source code. From creating a git worktree to merging the code back in with the merge queue functionality. A task should not be marked as complete until its changes are in the main branch. Use the harness's existing worktree and merge queue modules for this functionality.

A task's row on the board is read at a glance, so its name comes first and nothing else on the row may hide it. The row says little besides the name: the arrow of a high or low priority, state worth a flag (the main tree, archived, a borrowed slot, a merge in conflict), when (how long the task has worked or waited) and how many of its todos are done, then its buttons. What the task's session has to say (its context, the tokens it wrote, how fast, what they cost) is for the tooltip of the name and the session itself, not the row. When the window is short of room it is the informational part of the row that gives way: the todo count first, then the time; if the name still does not fit beside the buttons they go under it, with the rest of the row, rather than cut it. A name is cut only when it is longer than the window.

Tasks have a priority, kept simple: low, medium (the default) or high. It is the session's, as every priority is: a task's priority is its session's, and every task gets that session when it is submitted, so a task waiting for a slot already carries the level it will start with (nothing stores a priority on the task itself). When a limit on how many of a project's tasks may work at once holds tasks back, a free slot goes to the highest priority waiting, the oldest of those first, and the pending column lists them in that order. The user sets a session's priority wherever they are in the harness -- the `+`, `-`, `y` and `Y` keys, the session list's column and its `+`, `-` and `p`, which give every marked session the priority at once, the chat header's segment -- and the board's card keys and `/`-search set the task's session's; an agent does it with the session tools. Changing any other setting for many sessions at once leaves each session's priority as it was. A priority stops a task at work only for work the user sent back from review (below); the only other task stopped for a slot is one working in a slot lent by a task that waited on the user, once they answer.

Finished work waits for the user's review before it is merged (this can be turned off). Verifying a task merges its branch and completes it; sending it back with feedback has the same session work on it again in its own worktree, after which it waits for review again. Each round of feedback is kept with the task. Work sent back keeps to the limit on tasks at once, though its slot may have gone to a new task while it waited for review. With no slot free it pre-empts a task at work that it outranks: one of a lower priority, or one of its own priority that is not itself work sent back, since feedback on work the user has already reviewed goes before work of that priority that just started. A task whose turn is over but whose plan's workers or sub-agents still run is at work too, holding its slot through them. The task pre-empted goes back to the queue, its turn stopped and the work its session left running stopped with it, and later carries on where it stopped, its session told why in a message of the harness's own, as a session is when the harness starts again after it closed; what its workers and sub-agents were on is reported to it for then, and nothing of it restarts by itself. A task returned to the queue by hand stops its work the same way. Work sent back that outranks no task at work waits in the queue with its feedback, ahead of the work of its priority, and pre-empts as soon as it outranks one. A task that has waited on the user long enough (five minutes by default, an option that can turn it off) lends its slot, so the queue does not stand still behind a question nobody is there to answer: the next task starts in it, and the two cards say so. The user's answer takes the slot back at once, the task working in it going back to the queue as a pre-empted one does, to carry on where it stopped; a task still waiting on its workers or sub-agents keeps its slot, and a borrowed slot is never lent on. Nothing else pre-empts.

A new task is submitted one of three ways, picked in the compose box: Submit starts it at once; Refine has an agent write a sentence up into a brief task first; Plan has a strong model (the hard tier of the task model's provider) read the code, make the decisions and hand in a plan that a medium model then carries out. A write-up or a plan only reads -- the session gets the reading tools alone, its shell is read-only and offline, and a plan is nudged to hand itself in at about forty tool calls -- and takes no slot of the limit on tasks at once; the task then waits in the backlog until the user starts it. The model and thinking level of the write-up or the plan, and those of the work after it, are chosen per task above the compose box, the tiers only being the defaults. They are all a step has of its own: permission mode, interactivity, supervisor mode and where the task works are the task's, whatever step it is in, so they are set once, on a line of their own, not per step. Plan sits beside supervisor mode (see Supervisor Mode), which still decides whether the work of a submitted or refined task supervises; a planned task's work runs hands-on, since its plan is made already. The compose box shows the current mode's controls only: a line per step of its own, and the supervisor switch only where it applies.

Sessions which are ongoing but were not started as tasks can be onboarded into task mode, after which they are managed like any other task. The session controls (permission mode, thinking level, model, non-interactive mode, ect) should be controllable from task mode, both for a task's existing session and for the new tasks you submit, reusing the existing session controls instead of assuming a fixed configuration. New tasks should still default to the settings suited to full auto mode (ex., auto permission mode), but they are interactive by default: they only run in non-interactive mode when the config says so. The task mode UI must automatically refresh itself by subscribing to all the relevant events, the user should never have to manually reload it to see the current state of their tasks.

C-g on the board, or [Clear], shows every task again.

## Quick Search
The harness is searched in words, from anywhere, to help users find the commands they did not know about and do something quick in Emacs without remembering a key. `C-c h /` (or `/` in the menu) opens a small popout with a compose box: the box the chat and task mode use, not a prompt of its own, so it reuses that implementation -- its keys, its history, its look -- instead of duplicating it, and a buffer with no compose box of its own gets the popout's. A line there is a question ("how do I attach a file?", "where did I debug the merge queue?", "did I have a task about the question button?") or an order to manage tasks ("get rid of the pagination task"). It goes, with where it was typed, to the harness's cheapest model, which answers with JSON only: the commands to run, the sessions to open and the tasks the line is about, and what to do with the tasks. It is a command palette in Emacs, answered by a model. The popout lists what it found, each with its buttons: run a command in the buffer the search was opened from, or describe it; open a session, at the message where the search found the words when it found them in what was said there; see every match of the line in the sessions, as the session search shows them; show a task on its board. An order about tasks is proposed there, never done unasked.

Where the search is opened decides what it favours, and only favours. On a task board it favours tasks, in the session list or the conversation tree sessions, and anywhere else (a chat, a file, the settings page) commands, then sessions. The model is given all three -- the board's tasks, the other sessions and the harness's commands -- and one line saying where the user is and what to favour, so a session asked for on the board is still found. The task board's search is this same search, favouring tasks.

What it can reach: the project's tasks as the board reads them; every session, not only the sessions of tasks -- chats, BTW side conversations, sub-agents and forks, of every project, the one the user is in left out -- by their names and by what their transcripts say, through the harness's session search, which it is built on; and the harness's commands: its menu, the keys under its prefix, the commands each mode lists for the menu and every other harness command, each with the keys it has where the user is and what it does. Only the UI knows the commands, so it sends their catalogue along, and the walk over every symbol of Emacs that finds the commands is done ahead, while Emacs is idle, so that opening the search or sending a line does not repeat it each time. Only harness commands are offered and run, never any other command of Emacs.

Where the search favours sessions it looks in their transcripts before the model reads anything, for the words of the line that say something, so a session where the merge queue was debugged is found by what was said in it, not only by its name, and the model is handed what was found. The model's own look further searches transcripts the same way, in the session search's syntax: words in any form, every word, "phrases", prefix*, OR, -word.

A search does not settle for nothing. When what it favours has no answer, the model is told to look beyond it before giving up: its one look further may search every session's transcripts or the commands, and it says so in a note ("No task matched; these sessions mention it."). If it still answers with nothing, the search itself adds the sessions and commands that come nearest the query, with no further call of the model, and says so; it says there is nothing only when there is nothing at all.

The model never writes prose and is not a conversation: it gets the data, each round it makes is recorded as an internal session (see Internal Calls), so its cost is recorded like any other call, and its process starts as the box opens, so the answer comes sooner. It is the model task mode's search uses (`harness-tasks-search-model`, the provider's simple tier by default).

## Supervisor Mode
A top-level session on an expensive model plans and coordinates; workers on cheaper models make the changes. The supervisor investigates just enough to plan, because its tokens are the expensive ones (each of its calls reads the whole conversation again on the hard model) and the workers read the code they change. It then submits a plan of self-contained steps, each with a tier (simple or medium, see Model Tiers) that picks the model of its worker and the thinking level it runs at, a context (a fresh session, the default, or, for a short conversation only, a fork of the supervisor; see Cache Seeds) and the steps it waits for. The plan has a summary, which every fresh worker is given in its first message beside its own step, a line for each of the plan's other steps and the reports of the steps it waits for: the supervisor writes there, once, what the steps share (the approach, the interfaces, names and data shapes, and which step makes each) and not in every prompt. It writes each prompt for the tier of its step, a brief the size of a ticket for a medium worker and the edits file by file for a simple one, and splits the work no further than parallel work or a cheaper tier calls for, since fewer, larger medium steps cost less. The harness starts the workers and tells the supervisor, in messages of its own, when a step fails and when the plan has finished, so the supervisor never waits or polls: it checks the work, by what settles it most cheaply (the workers' reports, a diff, the test output) and not file by file, and decides, retrying a step (on a higher tier, if the model was not up to it) or planning again. A plan has no hard steps: the supervisor runs on the hard model, so a step that seems to need it is a sign the work is not broken down enough, and the supervisor makes the hard decisions itself and splits the work until every step is medium at most. Only a retry puts a step on the hard model, and none ever runs on the frontier one. A worker is an ordinary sub-agent session on a deliberately short context window, which the user can open and read like any other. Thinking follows the roles through the tiers: a supervisor thinks at the level of its provider's hard tier and a worker at the level of its step's tier, so DeepSeek plans at max while its workers think at low or high, and the many small steps cost less thinking than the plan. The plans live in the supervisor's record, so they survive a restart; a step that was running then is reported as interrupted. The session of a task supervises too: it hands in after its plan, and the task stays active while its workers run instead of going to review, holding its slot meanwhile. Its workers stop with the task when the task goes back to the queue, pre-empted by work sent back from review or returned by hand: their steps are interrupted and reported to the supervisor once, for it to retry when the task carries on. The mode is on by default -- a cheap model reads a new session's opening message and starts it supervising or hands-on, and a note in the harness's own voice says which, as the naming of a session reads "renamed to X": what the model answered is never shown, and the note never reaches the model. The note carries the two things to do about it as buttons, like the [Undo] of a lasting permission answer: stop judging new sessions and let the judge's mode stand for them, or put this session in the other mode, each with its undo and its redo, and the setting that decides them can be fixed instead ("always supervise" / "always hands-on") -- each session has its own switch in its header line, and sub-agents and side conversations never supervise. It is a plugin: the core got only generic hooks (a stop filter, a report of outstanding work and a way to stop it, a settings plist on sessions, a read-only sandbox), and removing the modules leaves the harness as it was.

### Research
The harness enforces the rule instead of asking for it, because a model that is only told to delegate keeps drifting into doing the work itself. What other harnesses found points the same way:

- Roo Code's Orchestrator mode ships without tools to read or write files or run commands, on purpose (its documentation says reads would fill the orchestrator's context), and users report that an orchestrator given edit and command rights tends to do the work itself.
- Claude Code's plan mode began as a prompt: a system reminder that the model must not make edits, which models ignored often enough that issues about edits made in plan mode keep being filed. Its permission layer enforces the block today (except in an interactive terminal with bypass permissions available). The lesson is that a read-only mode has to be a property of the tools, not of the text.
- Claude Code's `opusplan` has Opus plan and Sonnet execute, pairing Opus's reasoning for the plan with Sonnet's efficiency for the execution. That is the shape of this mode too: the expensive model decides what to do, and cheaper ones do it.
- Aider's architect/editor split has one model describe how to solve the problem and another turn that into edits. Separating the reasoning from the editing gave Aider state-of-the-art results on its code editing benchmark.
- Anthropic's post on its multi-agent research system found an Opus lead agent with Sonnet subagents beating a single Opus agent by 90.2% on its internal research eval, while multi-agent systems use about 15 times the tokens of a chat. Short, vague instructions made its subagents misread the task or repeat each other's searches. So each step is self-contained, and the plan's summary gives every worker what the steps share; the cost of the pattern is why workers are cheap models, start fresh and work on short windows.

### Enforcement
Four layers hold the rule, in order:

1. A tool allowlist (`agent/tools`): a supervising session is offered only reading, the web, coordination and the supervisor's own tools, so it never sees a tool that writes.
2. A permission stage at 8 (`permission/decide`), ahead of the jail, the mode and the judge: a call to anything else is denied for good, whatever the permission mode, rule or answer. It is what holds while the model still has an old tool list, right after the user switched the mode on, and it fails closed: a call it cannot check is denied.
3. A read-only sandbox for the one tool that can do anything, bash: its commands run with every directory read-only and no network (`tools/sandbox-options`, `sandbox/wrap` with `:read-only`), and where the sandbox cannot confine a command the session has no bash.
4. A stop rule (`agent/stop`): a turn ends only on a decision (a plan, or a reason none is needed). A model that stops without one is sent back with a reminder, twice at most, and after that the turn ends, with a hint in the transcript. A soft step budget nudges a long turn to submit its plan and never stops it.

A plan is approved by the user, never by a model. In ask mode the user approves each plan and each retry in a permission prompt, as with Claude Code's plan approval. In every other mode, and in a session the user left non-interactive, a second permission stage at 28 (after the mode and the rules, before the auto-mode judge) allows them, so the judge never rules on a plan. The judge sees one call with no context, so a plan that merely mentions something risky could be refused for words, not deeds. A plan changes nothing by itself: every call a worker makes goes through the whole permission chain in the worker's own session, judge included. A standing deny rule still denies a plan.

### Cache Seeds
A worker is fresh by default and forks the supervisor only while the supervisor's conversation is short, because no fork reads its parent's prompt cache. A provider's prompt cache serves only the model that wrote it, and only a request that starts with the very same prefix, the tools, the system prompt and the messages (see Cache Aware). A worker's request differs in all three: its system prompt names its own session's directories, its tools are not the supervisor's, and its model usually is not either. So a fork's first request writes the whole conversation into its model's cache, and every request after it reads it again; with a long supervisor conversation and several workers, that was most of a plan's cost. A fresh worker starts with a small context instead: the plan's summary, in which the supervisor writes once what the steps share, its own step, a line for each of the plan's other steps, the attempt before it when it starts again, and the reports of the steps it waits for.

A fork is still worth it for a conversation short enough to write into a cache once: the worker starts with what the supervisor learned, and the work is not gathered again with new costly tokens. A setting limits it: 20000 tokens by default, or no limit when it is nil. The conversation is estimated from its transcript at about four characters a token, leaving out the system prompt and the tools, which a fresh worker has too, and the thinking, whose signatures tie it to the supervisor's model. A plan with a fork step is refused when the estimate is past the limit: the refusal names the fork steps, the size and the limit, and tells the supervisor to make them fresh and to put what the workers need in the summary and their prompts. A fork step whose plan is past the limit all the same, because the plan was made before the limit existed or the limit was lowered since, starts from a compaction of the conversation, as a step that starts again does (below).

When a plan has two or more fork steps on one model they fork through a seed: a fork of the supervisor on that model, sent one tiny message so that its request writes the context into the cache once. Every worker is then a fork of the seed that sends the seed's system prompt word for word, and its first request reads the context instead of writing it. A seed is an ordinary session, listed and readable, and it is warmed again when its cache lapses. Any feature that forks a session several times can use one.

A fork step that starts again follows the same logic. A retry on a higher tier runs on a model that has never read the plan's conversation, and a fork never shares its parent's cache, so forking the supervisor would send all of it uncached at the expensive model's price, with the cold-cache gate none the wiser: a new fork has no cache to find cold. So the restarted step asks whether a warm seed holds the context on its model. If one does, the worker forks through it and reads the context cheaply. If none does, the fork is compacted before its first turn with the cold-cache default, a brief summary unless the user chose otherwise, and the conversation it replaced stays searchable. Either way the supervisor is told which, and the worker is told what the attempt before it ran on, how it ended and which session to read. A fresh step that starts again needs none of this: it starts a new fresh worker, with the same message and the attempt before it.
